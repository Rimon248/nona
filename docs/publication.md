# Публичный адрес и вход через Keycloak

Подготовлено 9 ноября 2026 года для существующего домашнего сервера. Сейчас `nona.server.basketref.ru` остаётся локальным: публичный A у Beget и статический A на MikroTik равны `192.168.3.24`, а Caddy использует `tls internal`. Никакой из файлов этого раздела сам по себе не открывает сайт извне.

## Выбранная схема

По примеру рефлаб.рф публичная DNS-запись Ноны будет указывать на внешний адрес домашнего подключения; MikroTik сохранит локальную запись `192.168.3.24`. На MikroTik уже есть проброс TCP 80/443 и UDP 443 на домашний сервер, поэтому для отдельного имени новое правило NAT не требуется. В Caddy локальный блок Ноны будет **заменён**, а не продублирован блоком `deploy/home/Caddyfile.public.example` без `tls internal`. Выпуск общедоверенного сертификата и доступ из мобильной сети необходимо проверить до сборки клиента с этим адресом.

На том же хосте уже работает Keycloak для BasketStat с публичным адресом `auth.basketstat-online.ru`. Для Ноны нужна отдельная область `nona`, клиент `nona-panel` и роль `nona-operator`. Области Keycloak разделяют пользователей и роли. Публичный Caddy-маршрут Keycloak должен добавить только `/realms/nona` и `/realms/nona/*` к уже разрешённым путям; `/admin/*` Keycloak и `/realms/master/*` остаются закрытыми. Файлы области и клиента без секретов находятся в `deploy/home/keycloak/`.

Контейнер `panel-auth` из `deploy/home/compose.auth.yaml` проверяет вход через Keycloak и роль `nona-operator`. Веб-маршруты `/admin` и `/admin/*` идут только через него; `/oauth2/*` обслуживает процедуру входа. Пока upstream `static://200` служит проверкой авторизации: полноценная панель управления пользователями, узлами и заданиями ещё не реализована. Публичное `/v1/*` идёт напрямую в API, где действует **отдельная** авторизация аккаунтов, токенов и устройств. Нельзя поставить интерактивный редирект Keycloak перед всем `/v1/*`: мобильный API использует JSON и Bearer-токены. Перевод мобильных аккаунтов на OIDC/PKCE — отдельная миграция, которую нельзя выдавать за выполненную.

## Секреты и порядок включения

1. Создать область `nona`, роль `nona-operator` и конфиденциальный OIDC-клиент `nona-panel` с единственным redirect URI `https://nona.server.basketref.ru/oauth2/callback`. В клиенте включить выделенный mapper аудитории `nona-panel` для ID и access token. Регистрация пользователей в области выключена. Создать пользователя `roman`, присвоить ему адрес, который владелец сообщил отдельно, и роль `nona-operator`. Адрес и пароль не хранить в репозитории. Почту отметить подтверждённой только после проверки владения адресом; OAuth2 Proxy по умолчанию отклоняет неподтверждённую почту. Не изменять область `basketstat`.
2. На сервере записать секрет клиента Keycloak в `/srv/docker/nona/secrets/panel_client_secret` без завершающего перевода строки и случайный 32-байтовый секрет cookie в `/srv/docker/nona/secrets/panel_cookie_secret`. Права каталога `0700`; файлы доступны только Docker-процессам, которым они смонтированы. Не выводить значения в логи или чат.
3. Разрешить OIDC-пути области `nona` в публичном блоке `auth.basketstat-online.ru`, не открывая административные пути Keycloak.
4. Запустить `panel-auth` через `docker compose -f compose.yaml -f compose.auth.yaml up -d` и проверить, что он доступен Caddy по внутреннему имени `nona-panel-auth:4180`. До публикации `/admin/` запрос без сессии должен отправлять на вход, а аккаунт без роли должен получать отказ.
5. Заменить публичную A-запись `nona.server.basketref.ru` у Beget на актуальный внешний IP домашнего подключения. Локальную запись MikroTik оставить `192.168.3.24`. Заменить блок Caddy на `Caddyfile.public.example`, предварительно сделав резервную копию и выполнив `caddy validate`; при ошибке вернуть прежний блок.
6. С устройства на мобильной сети без WireGuard проверить общедоверенный HTTPS, `GET /v1/info`, редирект `/admin/` на Keycloak, отказ без роли, 404 для `/readyz` и отсутствие доступа к `/admin` самого Keycloak. После этого можно указывать публичный адрес в сборке клиента.

Открытие сайта сделает домашний API доступным из интернета. До приглашения пользователей необходимы резервное копирование, внешний мониторинг, защита от перебора и завершённый отзыв индивидуальных VPN credentials на VDSina. Панель и API нельзя считать готовым VPN-сервисом только потому, что работает вход.
