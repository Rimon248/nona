# Реалистичный MVP

| Этап | Платформы | Результат | Проверка |
|---|---|---|---|
| 0. Каркас (сейчас) | Все четыре | Общий UI, запуск control API, схема, выбор узла, проверка подписи и хранилище проверенного пакета | `flutter analyze`, `flutter test`, `go test ./...` |
| 1. Сервер аккаунтов | Все четыре | Приглашения, вход, сессии устройств, отзыв, HTTPS, БД, аудит, выдача подписанного пакета | Чужое устройство не получает пакет; отзыв прекращает обновления и доступ на узлах |
| 2. Провижининг VDSina | Все четыре | Отдельные VLESS и Hysteria2 credentials на пользователя/устройство; безопасная синхронизация с существующим узлом | Создание, ротация и отзыв проверены без ручной раздачи ссылок |
| 3. Android | Android | `VpnService`, ядро, защищённое хранение, IPv4/IPv6, DNS, исключения приложений, переключение | Реальное устройство: российский тестовый адрес напрямую, зарубежный через VPN, отсутствие DNS/IPv6 утечки |
| 4. Apple | iOS, затем macOS | `NetworkExtension`, entitlement, Keychain, системные маршруты, пакетные обновления | Реальные устройства, подпись и установка; проверка маршрутов в Wi-Fi и мобильной сети |
| 5. Windows | Windows | Подписанный системный adapter/plug-in, установка и удаление, secure storage | Windows 10/11: подключение, перезагрузка, обновление, split routes и DNS |
| 6. Дополнительные узлы | Все четыре | AdminVPS и Aeza через тот же provisioner; выбор и failover | Отказ каждого узла не ломает рабочую сессию на другом |

Порядок выбран потому, что VPN-ядро нельзя полноценно проверить без реального аккаунта, действующих credentials и платформенного туннеля. Этапы 1–2 нужны до функционального мобильного клиента. Android служит первой платформой для сквозной проверки. iOS требует Apple Developer signing и Network Extension entitlement. Windows требует отдельной проверки подписанного сетевого компонента. Сроки зависят от доступа к устройствам, серверу и учётной записи Apple Developer; этот документ не выдаёт каркас за готовый VPN.

## Критерии первого рабочего релиза

- Один пользователь входит на Android и получает собственные VLESS+REALITY и Hysteria2 credentials без ручной ссылки.
- Выход из аккаунта удаляет локальные данные и отзывает refresh token; оператор может отозвать устройство и credentials на узле.
- Обновление набора узлов проходит только после проверки подписи и не портит последнюю рабочую конфигурацию при сбое.
- При недоступности VLESS клиент проверяет Hysteria2; выбор узла не меняется из-за краткого скачка задержки.
- Российские тестовые домены/IP и явно исключённые Android-приложения идут напрямую; зарубежные тестовые адреса — через VPN. IPv4, IPv6 и DNS проверяются отдельно.
- Системное разрешение VPN, статус и ограничения видимости описаны пользователю без обещания скрытности.

## Что потребуется от оператора перед интеграцией

Доступ к домашнему серверу и его публичному HTTPS-имени; способ администрирования существующего VDSina-узла; фактические порты и версии серверных компонентов; тестовые Android/iOS/macOS/Windows устройства; Apple Developer account для Apple targets. Эти значения передаются через защищённый канал и не помещаются в репозиторий или чатовые примеры.
