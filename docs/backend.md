# Сервер аккаунтов

Домашняя установка использует отдельный Keycloak Ноны и OIDC-режим API. Keycloak отвечает за пароль, вход и обновление токенов; PostgreSQL API хранит связь проверенного Keycloak `sub` с локальным аккаунтом, устройства и подписанные пакеты конфигурации. Самостоятельная регистрация включена, но новый аккаунт получает статус `pending` и не получает VPN-конфигурацию до решения администратора. Вход в приложении происходит через системный браузер с PKCE. Токены хранятся средствами защищённого хранилища ОС; при выходе приложение отзывает refresh token.

В OIDC-режиме API принимает `Authorization: Bearer <access_token>`, проверяет RS256-подпись по JWKS отдельного Keycloak, точные issuer `https://nona.server.basketref.ru/auth/realms/nona`, audience `nona-api`, `azp=nona-client` и сроки действия. `GET /v1/account` создаёт локальную связь при первом обращении. Старые маршруты `/v1/sessions*` отключены. Локальный режим с собственными паролями сохранён в коде для разработки, но на домашнем сервере не используется.

Миграции применяются по порядку из каталога `sql`, включая `008_account_deletion.sql`. Перед применением на действующей БД сделаны резервные копии. Не запускайте новый API против БД без всех миграций.

Удаление аккаунта доступно только исходному владельцу панели. Служба сначала отзывает все данные доступа на VDSina, затем удаляет пользователя Keycloak и данные Ноны. Пока отзыв не завершён, аккаунт остаётся в состоянии `deleting`. Субъект удалённого аккаунта сохраняется в закрытой таблице запрета повторного создания, чтобы старый токен не восстановил аккаунт.

API отдаёт только подписанный и зашифрованный для устройства пакет. Служба администратора раз в 15 секунд обрабатывает разрешённые устройства без действующего пакета и отзывает credentials при отмене доступа. Если выдача не удалась, повторная попытка откладывается на 1, 2, 4, 8 и затем максимум 15 минут; панель показывает число устройств с повторной выдачей, не раскрывая секреты или ответ VDSina. Ручные команды `admin provision-device ACCOUNT_ID DEVICE_ID` и `admin retire-device ACCOUNT_ID DEVICE_ID` остаются для обслуживания; локальная команда `admin install-configuration ACCOUNT_ID DEVICE_ID ENVELOPE_FILE` — для разработки. 11 ноября временный пользователь прошёл самостоятельную регистрацию: API создал аккаунт со статусом `pending`, панель показала заявку без устройств. На втором временном аккаунте проверены регистрация устройства, отказ в конфигурации до одобрения, автоматическая выдача после изменения статуса, подпись пакета, автоматический отзыв и повторный отказ API. Статус во втором тесте изменялся напрямую в БД; кнопки решения в панели ещё не проверялись. Оба аккаунта и их данные удалены. Текущая доступность VPN-транспорта не подтверждена.

`configbundle.BuildForDevice` шифрует данные узла для публичного ключа конкретного устройства и подписывает пакет. Адаптер `internal/node3xui` обращается к API клиентов 3x-ui по HTTPS с отдельным токеном, ограничивает операции идентификаторами `nona_` и не пересылает токен при перенаправлении. Живая операторская выдача на VDSina проверена для тестового устройства. Токен `nona-provisioner` хранится с правами `0600` только в `/srv/docker/nona/secrets/vdsina_3xui_token` на домашнем сервере; значение не включено в Git и сборки.

На действующем VDSina проверена версия 3x-ui `3.11.0`, а также наличие входов Hysteria2 и VLESS. API этой ветки управляет клиентами через `/panel/api/clients`, включая создание и удаление; точные схемы и поведение нужно сверить на конкретном узле перед первым изменением клиентов. [Официальная документация API клиентов](https://docs.sanaei.dev/docs/reference/api/clients/).

Развёртывание и адрес — в [инструкции домашнего сервера](../deploy/home/README.md) и [плане публикации](publication.md).
