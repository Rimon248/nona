# Сервер аккаунтов

Домашняя установка использует отдельный Keycloak Ноны и OIDC-режим API. Keycloak отвечает за пароль, вход и обновление токенов; PostgreSQL API хранит связь проверенного Keycloak `sub` с локальным аккаунтом, устройства и подписанные пакеты конфигурации. Самостоятельная регистрация включена, но новый аккаунт получает статус `pending` и не получает VPN-конфигурацию до решения администратора. Вход в приложении происходит через системный браузер с PKCE. Токены хранятся средствами защищённого хранилища ОС; при выходе приложение отзывает refresh token.

В OIDC-режиме API принимает `Authorization: Bearer <access_token>`, проверяет RS256-подпись по JWKS отдельного Keycloak, точные issuer `https://nona.server.basketref.ru/auth/realms/nona`, audience `nona-api`, `azp=nona-client` и сроки действия. `GET /v1/account` создаёт локальную связь при первом обращении. Старые маршруты `/v1/sessions*` отключены. Локальный режим с собственными паролями сохранён в коде для разработки, но на домашнем сервере не используется.

Миграции применяются по порядку из каталога `sql`, включая `008_account_deletion.sql`. Перед применением на действующей БД сделаны резервные копии. Не запускайте новый API против БД без всех миграций.

Удаление аккаунта доступно только исходному владельцу панели. Служба сначала отзывает все данные доступа на каждом настроенном узле, затем удаляет пользователя Keycloak и данные Ноны. Пока отзыв не завершён, аккаунт остаётся в состоянии `deleting`. Субъект удалённого аккаунта сохраняется в закрытой таблице запрета повторного создания, чтобы старый токен не восстановил аккаунт.

API отдаёт только подписанный и зашифрованный для устройства пакет. Служба администратора раз в 15 секунд обрабатывает разрешённые устройства без актуального пакета или без учётных записей на всех узлах и отзывает credentials при отмене доступа. Частичная выдача оставляет рабочие узлы в пакете и повторяет попытку через 1, 2, 4, 8 и затем максимум 15 минут; панель показывает число устройств с повторной выдачей, не раскрывая секреты или ответы узлов. Ручные команды `admin provision-device ACCOUNT_ID DEVICE_ID` и `admin retire-device ACCOUNT_ID DEVICE_ID` остаются для обслуживания; локальная команда `admin install-configuration ACCOUNT_ID DEVICE_ID ENVELOPE_FILE` — для разработки. 11 ноября временные аккаунты проверили регистрацию, ожидание одобрения, выдачу, подпись пакета, отзыв и повторный отказ API; тестовые аккаунты удалены.

`configbundle.BuildForDevice` шифрует данные узлов для публичного ключа конкретного устройства и подписывает пакет. Адаптер `internal/node3xui` обращается к API клиентов 3x-ui по HTTPS с отдельными токенами, ограничивает операции идентификаторами `nona_` и не пересылает токены при перенаправлении. 12 ноября Aeza подключён как второй узел после VDSina. Его Hysteria2 работает по UDP 443, VLESS+REALITY по TCP 8443. Токены панели и параметры соединения хранятся с правами `0600` только в `/srv/docker/nona/secrets`; они не включены в Git и сборки. Панель приняла отдельный токен, а provisioner создал по одной записи для 8 устройств на каждом из двух узлов. Реальный failover на клиенте ещё не подтверждён.

На обоих узлах проверены HTTPS API 3x-ui и наличие включённых входов. API этой ветки управляет клиентами через `/panel/api/clients`, включая создание и удаление; [официальная документация API клиентов](https://docs.sanaei.dev/docs/reference/api/clients/). В манифесте `nodes.json` порядок определяет приоритет: VDSina, Aeza, затем новые узлы. Инструкция развёртывания — в [инструкции домашнего сервера](../deploy/home/README.md).

Развёртывание и адрес — в [инструкции домашнего сервера](../deploy/home/README.md) и [плане публикации](publication.md).
