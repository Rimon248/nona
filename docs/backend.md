# Локальный запуск аккаунтов

Сейчас backend может создавать аккаунты, обслуживать вход, обновление токенов, выход, регистрацию и отзыв устройств. Он отдаёт заранее установленный подписанный пакет конфигурации только активному устройству владельца. Flutter-клиент после входа создаёт локальный X25519-ключ устройства и регистрирует его публичную часть, когда при сборке задан `NONA_API_BASE_URL` с HTTPS-адресом. Для домашнего сервера выбран адрес `https://nona.server.basketref.ru`; готовые файлы размещения и проверки находятся в `deploy/home/`. Автоматическое создание VPN credentials на VDSina ещё выключено. Это не публичный сервис до настройки HTTPS, секретов, резервного копирования и проверки на домашнем сервере.

Требуются Go 1.26+, PostgreSQL 14+ и доступ через локальный socket либо TLS с проверкой сертификата. Не передавайте пароль базы в командной строке и не коммитьте его. Для запуска задайте `NONA_DATABASE_URL` в защищённой конфигурации сервиса. HTTP-сервер с аккаунтами разрешает слушать только loopback; снаружи нужен HTTPS reverse proxy, который ограничивает запросы и не записывает тела входа и ответы с токенами в логи.

1. Создайте отдельную базу и роль с минимально нужными правами.
2. Примените по порядку `sql/001_accounts.sql`, `sql/002_devices.sql` и `sql/003_device_configurations.sql` через `psql` с `ON_ERROR_STOP=1`.
3. В терминале запустите `go run ./cmd/admin create-user ИМЯ`. Команда спросит пароль без отображения. Публичной регистрации нет.
4. Запустите `go run ./cmd/api` с `NONA_DATABASE_URL`. Без этой переменной сервер отдаёт только `/healthz`, `/v1/info` и ответ 503 на `/readyz`. После подключения к базе `/readyz` проверяет её доступность; этот маршрут должен оставаться внутренним.
5. Для временной ручной установки **уже подписанного и зашифрованного** пакета локальный оператор может задать публичные `NONA_CONFIG_KEY_ID`, `NONA_CONFIG_VERIFY_KEY_B64` и выполнить `go run ./cmd/admin install-configuration ACCOUNT_ID DEVICE_ID ENVELOPE_FILE`. Команда проверяет подпись, владельца, срок и возрастающую версию. Это вспомогательный путь до автоматического provisioner.

API: `POST /v1/sessions` (`username`, `password`), `POST /v1/sessions/refresh` (`refresh_token`), `DELETE /v1/sessions/current`, `POST /v1/devices`, `GET /v1/devices`, `GET /v1/devices/{id}/configuration`, `DELETE /v1/devices/{id}`. Маршруты устройств, получение пакета и выход требуют `Authorization: Bearer <access_token>`. Access token действует 15 минут, refresh token — до 30 дней и вращается, абсолютный срок сессии — 90 дней. В БД сохраняются только SHA-256 дайджесты случайных токенов. Пароли хешируются Argon2id с уникальной солью (64 MiB, 3 прохода, 1 поток). Повтор использованного refresh token отзывает сессию. Лимит попыток в приложении: 5 на имя за 5 минут и 30 глобально за минуту, максимум две параллельные проверки пароля. На reverse proxy нужен дополнительный лимит, поскольку лимиты процесса обнуляются при перезапуске.

Код шифрования индивидуальных credentials и клиентская расшифровка проверены общим вымышленным примером. API выдаёт только заранее установленные подписанные пакеты; он не создаёт credentials на VDSina и не является завершённым управлением ключами. Следующие обязательные работы до реального использования: автоматический провижининг и отзыв credentials на узлах, миграции и резервное копирование базы, мониторинг, настройки HTTPS и независимая проверка криптографического протокола. Клиент пока не использует полученный аккаунт для VPN-подключения.
