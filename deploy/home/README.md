# Нона на домашнем сервере

Это подготовка для Linux-сервера с существующим Caddy. В домашней сети 9 ноября 2026 года `homarr.server.basketref.ru` и `cockpit.server.basketref.ru` разрешались в `192.168.3.24` и отвечали по HTTPS через Caddy. Имя `nona.server.basketref.ru` ещё не было назначено. Файлы здесь не меняют работающий сервер и DNS автоматически.

## Адреса и границы доступа

- `https://nona.server.basketref.ru/v1/*` — клиентский API. Caddy передаёт запросы на `127.0.0.1:8080`; API не слушает внешние интерфейсы.
- `https://nona.server.basketref.ru/` — пока 404. Здесь позже разместится панель оператора, только после отдельной аутентификации, разграничения прав и защиты от CSRF. Пользовательские токены API не дают прав администратора.
- Парсеры, боты и задания обновления узлов будут отдельными процессами без публичных HTTP-портов. Их конкретные источники данных и действия пока не заданы.
- PostgreSQL и будущая очередь заданий доступны только локально. VPN-трафик клиента идёт напрямую к VDSina; домашний сервер выдаёт управление и конфигурации, но не пересылает пользовательский трафик. Интерфейс provisioner позднее позволит подключить AdminVPS и Aeza.

## Подготовка сервера

1. Проверьте, что сервер действительно использует Linux, systemd, Caddy и PostgreSQL 14+. Нужен Go 1.26+ для сборки. Эти файлы рассчитаны на запуск API на том же хосте, что и Caddy; если Caddy находится в контейнере, адрес `127.0.0.1` внутри контейнера указывает на контейнер, и upstream нужно настроить для фактической сети контейнеров.
2. Создайте отдельную системную учётную запись `nona` без интерактивного входа, базу `nona` и отдельную роль PostgreSQL с доступом только к этой базе. Примените по порядку миграции из `services/control-api/sql/001_accounts.sql`, `002_devices.sql`, `003_device_configurations.sql` с остановкой при ошибке. Сохраните резервную копию базы перед миграциями на действующем сервере.
3. Соберите API из `services/control-api`: `go build -o control-api ./cmd/api`. Установите бинарный файл в `/opt/nona/bin/control-api`, владелец `root`, права `0755`.
4. Создайте `/etc/nona/control-api.env` с `NONA_DATABASE_URL=...`. Файл не входит в репозиторий; установите владельца `root` и права `0600`. Используйте локальный PostgreSQL socket с peer authentication для роли `nona` либо отдельный пароль с ограниченными правами. Никогда не помещайте строку подключения, закрытый ключ подписи или ссылки VPN в Caddyfile, приложение или Git.
5. Установите `nona-control-api.service` в `/etc/systemd/system/`, проверьте `systemd-analyze verify`, затем запустите службу. Локально проверьте `curl --fail http://127.0.0.1:8080/readyz`: ответ 200 означает, что аккаунтная БД доступна; 503 означает, что она не готова. `/healthz` проверяет только работу HTTP-процесса.
6. В существующую конфигурацию Caddy добавьте блок из `Caddyfile.nona.example` один раз. Проверьте `caddy validate --config /etc/caddy/Caddyfile` и только затем перезагрузите Caddy. Маршрут `/v1/*` сохраняет префикс пути, который ожидает API; остальные пути возвращают 404.
7. В используемой DNS-зоне добавьте `nona.server.basketref.ru`, направив его на домашний Caddy так же, как действующие `homarr` и `cockpit`. Не заменяйте существующие записи. Если это только локальная зона и адрес `192.168.3.24` не доступен из внешней сети, клиент вне дома не сможет обновлять аккаунт и конфигурации. До обещания постоянного доступа проверьте DNS, TLS и `GET /v1/info` с Android через мобильную сеть без домашнего Wi-Fi. При недоступности дома уже сохранённая действительная конфигурация должна оставаться у клиента.

## Перед реальным запуском

Сейчас API выдаёт только заранее установленные подписанные и зашифрованные пакеты. Создание и отзыв индивидуальных VLESS+REALITY и Hysteria2 credentials на VDSina ещё не реализованы; нет рабочей панели оператора и рабочих заданий парсеров/ботов. До выдачи пользователей нужны автоматизация отзыва на узле, резервное копирование и восстановление БД, мониторинг, TLS с доверенным сертификатом и отдельная проверка криптографического протокола. Доступность домашнего адреса зависит от DNS, маршрута извне и работы домашнего сервера.

## Проверка после настройки

- С сервера: `/readyz` возвращает 200 только с доступной БД.
- Из сети клиента: `https://nona.server.basketref.ru/v1/info` возвращает JSON и доверенный сертификат.
- Из сети клиента: `https://nona.server.basketref.ru/` и `/readyz` возвращают 404; панель и диагностика не открыты публике.
- `ss -ltn` показывает API только на `127.0.0.1:8080`, PostgreSQL не доступен снаружи, а будущие фоновые службы не открывают портов.
